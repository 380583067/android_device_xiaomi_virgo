# Virgo userdebug：setenforce 1 后黑屏/框架重启修复

设备 `a1152088`，构建 `21.0-20261023-UNOFFICIAL-virgo`，Android 14，
`ro.build.type=userdebug`。本次只修改源码、生成补丁、定向编译校验并做 ADB
运行验证；没有完整编译 ROM，没有刷写 boot/system，也没有更换运行中的内核。

## 故障证据

原始日志及完整诊断文件：`/run/media/root/tank/virgo-selinux-20261024/`。

- `active-crash.txt`：Enforcing 下唤醒并打开设置，SystemUI/Settings 的
  RenderThread 出现 SIGSEGV；Zygote 随后以
  `JNI FatalError called: (zygote) Unable to stat 4` 退出。
- `active-mid-dmesg.txt`：对应拒绝包括应用访问
  `/system/vendor/lib/hw/gralloc.msm8974.so`（误标为 `vendor_file`），
  Zygote 对 `/sys/kernel/debug/tracing/trace_marker` 的 `getattr` 被拒绝
  （误标为通用 `debugfs`）。
- 同时存在 CPU hotplug、health、传感器及 Power HAL 的通用 `sysfs` 拒绝。
- `device-policy.cil` 已包含旧 0010 补丁的 CPU/BMS genfs 定义，但实机标签仍为
  通用 `sysfs`；因此不能靠重复添加相同策略解决。
- 当前 Linux 3.4 `hooks.c` 仅对 procfs 执行逐路径 genfs 匹配，其他伪文件系统
  直接继承 superblock 标签。这是原有 genfs 规则没有生效的内核原因。

内核实现参考 Linux v4.9 的
[selinux_genfs_get_sid](https://github.com/torvalds/linux/blob/v4.9/security/selinux/hooks.c)，
按本树旧 API 回移，保留 proc PID 路径处理，不改动 SELinux 判定逻辑。

## 按源码路径归类的新增补丁

1. `kernel/xiaomi/virgo/0004-label-sysfs-and-debugfs-with-genfs-contexts.patch`
   - 修改 `security/selinux/hooks.c` 和 `security/selinux/include/security.h`。
   - 增加 `SE_SBGENFS`，使 sysfs/debugfs/tracefs/pstore 使用已有的逐路径标签；
     procfs 保持原来的 PID 目录处理方式。
2. `device/xiaomi/virgo/0011-fix-enforcing-passthrough-hals-and-service-domains.patch`
   - 修改 `sepolicy/file_contexts`、`sepolicy/genfs_contexts`。
   - 新增 `sepolicy/touch.te`、`sepolicy/power.te`、`sepolicy/sensors.te`。
   - 标记实际由 Android 进程直加载的 gralloc、sensor wrapper、MultiHal、
     libsensors.leo 和 camera-provider 库为 `same_process_hal_file`。
   - 将 software gatekeeper、Xiaomi light、Virgo touch 可执行文件标为对应的
     既有 HAL exec 类型，避免继承 `init` 域。
   - 为物理 LED、IIO 驱动 sysfs、触摸按键开关和两组 GPIO-key 开关补标签。
   - 将该板五个 IIO 字符设备标为 `virgo_sensor_device`，仅为现有
     system_server 内的 legacy passthrough sensor HAL 增加采集所需的读取权限。
     五个节点实机名称依次是 distance、als、pressure、icm30628、inv_sh-activity。
   - Touch/Power 使用各自专用 sysfs 类型与对应 HAL 的访问规则。

这两份补丁已应用到当前源码。保留所有先前补丁及其他已有改动。
没有新增 permissive 域，没有新增通用 sysfs/debugfs/vendor_file 的放行规则。
默认 kernel cmdline 的 `androidboot.selinux=permissive` 保持原设置。

## 编译及补丁校验

- `check.sh` 完整反向检查及顺序回放：49 份补丁全部 Applied。
- 设备树、内核 `git diff --check` 通过。
- 使用现有 ARM GCC 4.9 和独立输出目录，只编译
  `security/selinux/hooks.o` 成功；日志为 `kernel-config.log`、
  `kernel-hooks-build.log`。没有编译完整内核镜像或 ROM。
- 将本次新增 `.te` 和 genfs 内容并入本机保存的 Android 14 预处理 vendor
  policy，经过 checkpolicy、version_policy、secilc、checkfc 验证成功。
  可复现脚本为诊断目录的 `verify-source.py`，结果为
  `source-policy-build-configured.log`。
- 该定向校验使用保存的预处理策略，不等同于重新运行当前整树的 Soong 策略构建。
  旧 QCOM 树 `device/qcom/sepolicy-legacy/sepolicy.mk` 原本就设置了
  `SELINUX_IGNORE_NEVERALLOWS := true`，合并时按原配置使用 `secilc -N`。
  严格 neverallow 尝试仍会遇到历史 QCOM 策略冲突，日志为
  `source-policy-build.log`；本次没有修改此开关，也不声称严格 neverallow 全部通过。

## ADB 验证方式与边界

原始二进制策略、源文件及 vendor file_contexts 已分别保存在
`device-policy`、`source-before/`、`vendor-file-contexts.before`。

在运行中的旧内核上，将既有策略 genfs 标签临时应用到对应伪文件节点，修正
vendor 库/可执行文件的 xattr，并加载只补充本次专用类型和权限的内存策略。
运行策略由原设备策略加 `runtime-additions.cil` 编译得到，不替换磁盘上的策略文件。

最初复现引发了一次框架崩溃；标签修正后又主动重启了一次 Android 框架，
恢复相机/传感器初始化。Kernel boot ID 始终为
`a169b6f5-b226-4a90-bcce-91fc219128f3`，没有整机重启。

最终证据见诊断目录：

- `final-validation.log`、`final-state-*.txt`：逐次确认 Enforcing、核心 PID、
  boot animation 状态与 boot_completed；含休眠唤醒、设置/Wi-Fi/蓝牙/显示页面打开。
- `final-sensors.txt`：传感器枚举及近期事件。只有枚举不代表所有传感器精度、
  方向和物理旋转已验证。
- `final-network.txt`：Wi-Fi 连接状态和蓝牙 ON 状态。未验证外部蓝牙配对、
  全部 Wi-Fi AP、SIM 通话/数据或 GPS 定位。
- `final-camera.txt`：两路 HAL1 相机枚举。本轮没有证明拍照、录像、Camera2
  预览等功能通过，不能把相机数量当作功能验证。
- `final-screen.png`：Enforcing 测试期间可正常显示的设置页面。
- `final-denials-summary.txt`：最后窗口的拒绝分类；不将与本次崩溃无关的
  RIL 日志节点或全局 shim 探测拒绝批量转为 allow。

验证结束恢复 `Permissive`，并停止本次自动恢复进程。临时内存策略和
sysfs/debugfs/dev 节点的重标记会在重启后丢失。**永久生效需要编译并安装包含
新内核和新 SELinux 策略/文件标签的版本，不能只更新 system 而继续使用旧内核。**
本轮尚未验证新内核启动、Enforcing 冷启动或完整功能回归。

## 源码重编译后的复测

先确认实际 OUT_DIR 和挂载盘，再使用当前设备的 lunch 目标：

```bash
source build/envsetup.sh
lunch lineage_virgo-ap2a-userdebug
```

编译由用户自行执行。安装对应内核和系统后，先检查 boot_completed、genfs 节点
标签及 HAL 进程域，再手动 `adb shell setenforce 1`，复测唤醒、设置界面及实际
硬件功能。必要时 `adb shell setenforce 0` 恢复，以新日志定位尚未覆盖的路径。
